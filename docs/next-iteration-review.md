# eKYC service review and next-iteration backlog

Reviewed 16 November 2026. Scope covers the current working tree on `main`, including uncommitted v2 changes, the four bundled policies, Rust services, PostgreSQL migrations, provider mocks, the operator portal and the published API guide. Commit `9ea820b` is the baseline. It does not contain the full snapshot reviewed.

The original backlog contained **24 findings** across six reviews. The subsequent implementation and the added presentation review are tracked in the [development iteration](#development-iteration). Seven are P1, fourteen are P2, and three are P3. Two P1 items apply specifically if the local portal becomes a staff tool.

## Original priorities

1. **Protect existing audit history before a populated upgrade.** Ordinary service startup runs the migration that drops the v1 case and revision tables. The current migration test explicitly expects both tables to disappear. Start with **ARCH-01** if any deployment still holds v1 records.
2. **Make lending decisions safe when evidence changes or arrives out of order.** Start **ARCH-02** and **ARCH-03** together. Give QA a deterministic test for a changed issuer binding and a second test for an adverse fact committed during approval. Agree on the vendor observation-time and outstanding-screening contracts in **ARCH-04** and **ARCH-05** before connecting a real provider.
3. **Ship the small, verified user-facing fixes in parallel.** Qualify the lending decision (**PM-03**), align reviewer-note validation (**UX-01**), and fix the published reporting-error schema (**QA-01**). Each has a concrete example below.
4. **Decide who operates the review queue.** If an institution already owns investigation intake and staff identity, test that handoff. If the portal will be staff tooling, plan **PM-01** and **PM-02** before rollout. Both are deployment decisions for the current local demo.

**Priority and evidence.** P1 identifies a possible incorrect decision, loss of history, or missing operational control under the stated condition. P2 identifies a material workflow, integration, or engineering gap. P3 identifies a smaller usability or documentation improvement. *Observed* means a test, browser inspection, or API request demonstrated the stated behavior. *Traced* means the implementation supports the finding and the proposed failure scenario still needs a dedicated test. Owners below are suggested roles.

## 4. Technical architecture

### ARCH-01 · P1 for populated upgrades · Preserve legacy history

Both API and worker startup apply pending migrations. Migration 0007 drops the two v1 history tables. The design calls for a prior drain and export, but startup has no archive precondition. The populated migration test confirms the tables disappear while the queued v1 decision survives. The relay can subsequently send that v1 payload to a receiver expecting v2. *Observed in the database test and traced through delivery.* [Startup](../adapters/postgres/src/lib.rs#L68) · [Removal](../adapters/postgres/migrations/0007_unified_cases.sql#L3) · [Upgrade test](../adapters/postgres/src/tests/migration.rs#L55) · [Delivery](../adapters/webhook-events/src/delivery.rs#L32) · [Deployment guidance](design.md#L29)

**Done when** a default startup against populated v1 storage preserves recoverable case revisions or stops before removal. Rehearse a drained upgrade, restore a sampled case and its full revision history from the archive, and demonstrate delivery or prior draining of queued v1 events. Check already-upgraded deployments for a recoverable archive before scheduling further work.

### ARCH-02 · P1 · Settle checks when issuer bindings drift

The worker handles an invalid issuer response by blocking the check and preserving a positive screening alert. A structurally valid response can instead fail the case’s pinned policy, for example when the issuer renames the screening method. That error exits settlement before either action. The expiry handler uses the same settlement path. If the mismatch persists, a check can remain pending after both the result and its deadline have run. *Traced.* [Binding validation](../crates/domain/src/product/evidence.rs#L46) · [Revalidation](../adapters/restate/src/product.rs#L215) · [Settlement](../adapters/restate/src/product/settlement.rs#L31) · [Expiry](../adapters/restate/src/product.rs#L171)

**Done when** a changed method during a pending operation produces a durable, actionable state through both the result and expiry paths. A received positive yields one investigation alert with its original operation. Restoring a supported binding permits recovery.

### ARCH-03 · P1 for cross-product reuse · Recheck evidence at decision commit

Lending reads the subject’s facts in a Restate step. PostgreSQL opens the transaction that publishes approval afterward. A wallet case can publish a substantive adverse fact between those operations. Lending can then commit a terminal approval from the older fact set. The existing design discloses this timing window. *Traced. Concurrent publication was not exercised in this review.* [Fact read](../adapters/restate/src/product.rs#L193) · [Approval transaction](../adapters/postgres/src/product.rs#L64) · [Adverse publication](../adapters/postgres/src/product.rs#L85) · [Documented limitation](product-verification.md#L63)

**Done when** a deterministic two-case test commits a relevant adverse fact between the reuse read and the approval write. The write detects the change and re-evaluates before issuing a decision or event. Define the separate freshness guarantee for issuer revisions obtained outside PostgreSQL.

### ARCH-04 · P1 for real provider reuse · Separate observation time from receipt time

The synchronous adapter records the time an HTTP attempt returns. A vendor may already have saved the result and return it on a later retry. Reuse rules order observations by that timestamp. Under delayed retrieval, an older pass can appear newer than an intervening adverse observation. The mock already models saving a result before delaying its reply. *Traced. The ordering scenario remains untested.* [Attempt timestamp](../adapters/restate/src/checks.rs#L231) · [Reuse ordering](../crates/domain/src/product/policy.rs#L147) · [Mock cache](../mocks/server.py#L77)

**Done when** the adapter supplies a stable vendor evaluation time or sequence across delivery attempts and records receipt time separately. A delayed retrieval of an older pass cannot supersede newer adverse evidence. Define eligibility for providers that lack a reliable ordering signal.

### ARCH-05 · P1 for real sanctions providers · Recover vendor results after a final timeout

The held-response drill passed. A positive that still reaches the worker after the case closes produces the expected alert. A different path remains open when the vendor completes screening but the final HTTP response never reaches the worker. Retries stop once the operation is inactive, and the normal adapter has no independent result lookup. A replacement screen can finish without the earlier result reaching investigation. *Traced, with the bounded late-response drill observed.* [Operation lifecycle](../adapters/restate/src/checks.rs#L103) · [I/O timeout](../adapters/restate/src/checks.rs#L214) · [Existing drill](../scripts/late_screen_smoke.py#L48)

**Done when** the selected vendor’s callback or reconciliation mechanism can report the original operation after the local retry budget expires. A delayed positive produces one logical investigation event with a stable ID, even after a replacement decision. Track unresolved operations until that mechanism gives a definitive outcome.

### ARCH-06 · P2 · Expose command-path readiness

API readiness checks PostgreSQL only. The worker can start with both issuer settings absent, and then every case opening needs an unavailable resolver. The registration script also treats a matching worker URI as sufficient without checking its advertised service revision. An operator can see a healthy API while new cases cannot start. *Traced.* [API readiness](../apps/http-api/src/server.rs#L43) · [Resolver startup and use](../adapters/restate/src/evidence.rs#L33) · [Registration](../scripts/register.py#L16)

**Done when** an omitted mandatory issuer configuration is identified on startup, an unregistered or stale command deployment is visible to operators, and an integration check distinguishes read availability from the ability to open a case.
