# Provider routing with Restate and PostgreSQL

Implementation plan for the eKYC service, based on `main` at `e65d783`, 16 November 2026.

## Outcome

An operator can run an 80/20 address-verification pilot, take vendor A offline, watch eligible new checks move to B within its contract, and list every case still waiting for A. When A recovers, traffic returns in measured steps. The final drill applies a stricter policy to a sanctions check whose original answer was lost. Its acceptance criterion is that a replacement clear cannot publish an approval while that original is unresolved.

Move provider HTTP concurrency to Restate for the new dispatch path across check kinds. Keep the rolling dispatch rate, vendor throttling, circuit state and spend reservations in PostgreSQL. Introduce automatic multi-vendor routing for **address first**. The existing caller quota stays at the HTTP API boundary, where it can return an immediate 429 and `Retry-After`.

## 1. Establish who owns each decision

| Decision | Owner and key | Observable guarantee |
| --- | --- | --- |
| Which vendors may verify this evidence? | Versioned institution, product, use-case and check policy, with approved methods, thresholds and issuer bindings | A live traffic change can only narrow the approved set. Historical cases keep their original decision rules. |
| Which vendor gets this requirement? | Case coordinator and persisted route selection per requirement, evidence revision and selection sequence | Retry or restart recovers the same decision. Every diversion or replacement records a reason and predecessor. |
| How many HTTP calls may run? | Restate concurrency rule on the actual upstream concurrency account/pool. Submit and lookup can use child limit keys. | All routes sharing the pool draw from its cap. Waiting for a callback, a quota window or a retry takes place outside the attempt handler. |
| May another call start now, and what can it cost? | PostgreSQL rolling counters and throttling for the vendor's contractual rate bucket(s), plus a ledger for the applicable billing account, currency and period | Two routes sharing a credential can consume the same rate budget. Concurrent reservations cannot exceed an approved spend ceiling. |
| Is this dependency healthy enough to try? | PostgreSQL breaker for the vendor and check/endpoint failure domain, with a generation and a single expiring probe claim | A transient address outage at A leaves independent B healthy. A late result from an older generation cannot close a newer circuit. |
| Can the case finish? | Case domain policy and the transaction publishing the case revision and outbox event | A routing override cannot discard a finding, clear a sanctions hold or authorize a product decision. |

Give each route explicit references to these contract domains. Two credentials might share an upstream account. One vendor might have independent submit and lookup endpoints that still share an account-wide rate cap. Configure both parent and sublimits where the contract specifies them. Use stable opaque identifiers and keep the mapping to credentials server-side. Pin the route identity, policy and tariff revision for audit. Apply the current operational ceiling for the same contract before each send, including old work. Validate configurations against the rule book at startup. Where the real contract cannot be represented by Restate's scope hierarchy, document the missing constraint and qualify that route before enabling it.

**Starting point.** The current SQL groups ordinary vendor calls by check kind. `ProviderChecks` performs the vendor call inside a journaled step and later releases its SQL lease. Sanctions lookups follow a separate polling path. The code already has a per-case writer, distinct vendor identities, stable operation IDs and an atomic decision outbox. ## 2. Build one routing policy for normal service, outage and recovery

**Eligibility and placement.** At case opening, pin an immutable routing-policy version. Resolve an issuer-authorized candidate binding for each eligible vendor against the same institution, subject, check, evidence identity and revision. Store the method, approval rule and protected vendor locator per binding. A new vendor or score scale needs separately validated thresholds before the policy can treat its finding as equivalent. Add a versioned issuer response because the existing binding rejects unknown fields. Adapt an old response as a singleton candidate. If B has no authorized binding, continue with an eligible A, wait, or request a fresh capture according to policy. An operator cannot manufacture a B locator. [Evidence model](../../../crates/domain/src/product/evidence.rs) · [Issuer resolver](../../../adapters/restate/src/evidence.rs) · [Current issuer contract](../../../apps/portal/public/issuer-contract.json)

Support two explicit placement modes. For weighted routing, use a stable, versioned hash of the policy salt and requirement identity, with a canonical vendor order and published bucket boundaries. For primary/backup, walk the approved priority order. Start with eligibility, apply current operational restrictions, then persist the candidates, bucket or priority, target, fallback reason, evidence revision and override version **before dispatch**. Persist selections idempotently under a unique requirement, evidence revision and selection sequence. Under the normal address fixture, both vendors are eligible and the weights are 80/20. Measure the policy split over eligible first assignments. Report retries, replacements, single-eligible cases and outage diversions separately.

Give the policy an explicit degraded state. Sustained p95 latency above its threshold, with sufficient traffic, reduces A's permitted share before calls begin timing out. Calculate latency and technical failure rates per route and exclude business findings from failure counts. Persist the effective share, its cause and the evidence window. Configure separate entry and exit thresholds so one slow or fast response cannot repeatedly change placement.

| Event | Required behavior |
| --- | --- |
| A is paused, draining, or its breaker is open before submission | Divert eligible new requirements to B. A previously assigned, provably unsent operation may be retired atomically and linked to a new assignment. Fence any stale queued A invocation at the send boundary. B's rate, concurrency and spend ceilings continue to apply. |
| B is full or over budget | Wait within the original deadline when capacity or budget can become available. On expiry, expose `PROVIDER_BLOCKED`, a reason, owner and recovery action. If the policy permits no possible send before expiry, surface that reason early. A late scheduler wakeup must perform zero vendor calls. |
| A may have accepted the request | Record A as outstanding. Retry A using its original vendor operation ID or use its result-only lookup. A transport timeout, generic HTTP error or missing lookup response is ambiguous. If policy authorizes a B replacement, allocate a new B operation ID and B binding under the same requirement. Preserve both histories and the original deadline and attempt budget. |
| A returns a verification finding | Apply the pinned evidence, correction or review rule. A stale proof prompts correction. A sanctions hit prompts investigation. A finding cannot trigger routing to seek a pass. If previously authorized concurrent work yields conflicting results on the same revision, retain both and send the conflict for review. |
| A recovers | An eligible probe after cooldown is admitted once per breaker generation. A transient failure reopens the circuit. After success, restore A's share among **new** eligible assignments in steps with a minimum sample, dwell time, error ceiling and latency threshold. Pause or step back on regression. Scheduled B work stays at B. Queue release observes the same limits as fresh work. |

When the cooldown expires, allow the first eligible new request to compete for a probe even when A's ordinary share is zero. If there is no eligible traffic, keep A waiting for a probe, or use a vendor-approved synthetic probe if the contract provides one. An abandoned probe claim expires. Its unique attempt token and generation fence prevent a late completion from an earlier probe from closing the circuit. Test recovery starting at zero normal traffic.

Proposed address pilot default: follow a possibly accepted A operation to an authoritative answer or assigned review. A separate test policy permits a linked B replacement and holds automated completion while A's result could change the decision. This makes the ambiguous-replacement flow testable without deciding production risk policy for the institution. Add a result-only address lookup to both pilot adapters and mocks. A terminal “not accepted” must fence a delayed send. Vendors without such a contract remain visibly unresolved until their approved recovery procedure completes. ## 3. Make retries, accounting and deadlines survive a crash

Use three identities. A **requirement** identifies what the case needs for one evidence revision. A **vendor operation** identifies one logical check at one vendor and supplies its idempotency key. A **transport attempt** identifies a particular submission or lookup. A retry at A keeps A's operation ID. A replacement at B gets its own operation ID. Persist each operation's provider, method, protected binding, predecessor, decision reason, deadline and owner. Replace the current one-flight-per-check assumption for routed work so a B replacement can coexist with an unresolved A. [Case dispatch](../../../adapters/restate/src/product/dispatch.rs)

1. The unscoped coordinator persists the route choice idempotently, then requests one short stateless Restate attempt under the concurrency pool and `submit` or `lookup` limit key. Keep case callbacks and settlement on the original case identity. Scope changes in Restate also change the namespace for object keys and idempotency. [Restate flow control](https://docs.restate.dev/services/flow-control)
2. Once Restate admits the attempt, enter one replayable I/O step containing the authorization transaction and the outbound HTTP call. Immediately before HTTP, one short PostgreSQL transaction checks eligibility and atomically claims first use of this attempt token. It also performs the accounting below. Only the transaction's first consumer may send. A submission requires a current assignment, matching evidence revision, unexpired deadline, valid override, available attempt budget and permission from the breaker. A lookup requires an outstanding original operation and an authorized retrieval route; it remains eligible after submission expiry, replacement or a pause on new traffic. Both consume the applicable rate, throttle and spend budgets. Lock multiple budget rows in a consistent order. Atomically debit the budget for this action and record the single-use attempt authorization, rolling-rate charge, spend reservation, possible-send marker and any probe claim. A and B spend from the same requirement submission budget. Lookups spend from their separate retrieval budget. The transaction ends before network I/O. A refused admission returns the earliest retry time/reason; the short handler exits and its caller owns the durable wait.
3. Within that same I/O step, check the remaining time immediately before sending to the vendor with its stable operation ID. Abandon an expired authorization and reconcile its reservation. An override that arrives after authorization can leave an in-flight request. A strict remote wall-clock cutoff requires an expiry the vendor itself enforces. Persist the classified result, timing, billing effect and any fenced breaker transition. A verification failure is a business result. A vendor 429 applies its contractual `Retry-After` to the correct shared bucket. Qualifying transient errors affect the breaker. Keep the replayed journal, attempt ledger and vendor receipt consistent through idempotent updates. A replay that sees a consumed token reads the saved result or reports an unknown outcome; it cannot reuse the send authorization. Disable implicit HTTP retries and redirects that could send again without authorization. A fresh physical send needs a fresh authorization.
4. A restart between intent and HTTP completion may leave a conservative possible-send record even when the vendor received nothing. Count it until reconciled. Reserve cost in integer minor units against the configured billing unit, currency, account, period/time zone and approved ceiling. For a per-operation tariff, deduplicated retries share one reservation; per-request contracts account for each chargeable attempt. Attribute B's charge independently. Reconcile reservations against authoritative receipts or invoices, including period rollover. Show estimated, confirmed and uncertain amounts separately.
5. Enforce a single submission deadline and attempt budget across retries and vendors. The coordinator owns capped exponential backoff and jitter. Result-only lookup has its own bounded rate and concurrency lane and continues for a previously submitted operation after the case deadline. Escalating aged work assigns an owner while preserving lookup history. HTTP timeouts and worker death can leave the vendor executing remotely. Vendor idempotency and lookup remain part of the contract. [Retry and backoff guidance](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

**Avoid replaying a denial forever.** Give each coordinator request for admission a durable sequence number. Replay of that request uses the same Restate invocation identity. After a completed “wait and try again” response, issue a fresh admission invocation so it can see fresh quota state. A denial consumes no vendor attempt or billable reservation. The transition to “may have sent” consumes a submission attempt even if the worker subsequently loses its reply.

**Capacity example for the drill.** Give B an actual account cap of four concurrent calls. Limit its `submit` child to three and let lookup use the same parent, leaving room for one lookup even when submissions are backlogged. Where submit and lookup share a rolling rate contract, reserve rate capacity in PostgreSQL as well. Keep quotas configurable and validate that the reserve leaves viable submission capacity. Ordinary SQL admission no longer counts in-flight requests. The one-probe claim and spend reservations serve separate purposes.

Persist indexed records for route assignments, vendor operations and attempts; contract windows and billing reservations; breaker generations and probes; operational overrides, review obligations and their audit events. Enforce unique keys for each logical operation, transport attempt, billable unit, escalation and investigation event. Protect customer evidence locators from reports and logs.

Use separate lookup funding within the approved ceiling if retrieval is billable. Establish whether the vendor contract counts active HTTP calls or outstanding remote jobs. An accepted asynchronous job can outlive the HTTP request. A job-based contract requires vendor-side admission or a conservative outstanding-job reservation settled by an authoritative result. The pilot measures HTTP-call concurrency.

## 5. Operator and finance acceptance

- **Risk/product** version the approved roster, evidence methods and thresholds, permitted fallback reasons, treatment of unresolved originals and escalation age. The pilot can use reviewed, versioned configuration for publication. Keep the issuer decision and route eligibility explainable for any case.
- **Operations** can pause new submissions, drain A, cap its share, start a recovery ramp or roll it back. Persist authenticated actor, institution and product scope, reason, issue time, expiry, change version, and before/after values. Use optimistic concurrency and command idempotency. Expiry restores the effective policy subject to current health. Route health and capacity can lower the permitted share. Operators cannot broaden risk eligibility or dispose of screening findings. A shared account override needs authority over that scope.
- **Pause and drain have distinct effects.** Pause prevents further outbound submissions at the final admission check, including queued attempts. Drain stops new placements while previously assigned operations finish within policy. Both allow authorized result retrieval for work already sent. Record the time the override took effect and any request already past its send boundary.
- **Staff and finance** get a per-case timeline and an indexed queue by vendor, age, owner and state. Reports distinguish eligible first assignments, actual sends, distinct vendor executions, cached responses, assigned fallbacks and successful rescues. Reconcile all pilot requirements to a terminal decision, an actionable block or an outstanding operation with an owner. Display booked and pending cost by currency and period. Use aggregate metrics for rate, latency, errors, queue depth, breaker state and lookup lag; keep customer identifiers in access-controlled drilldowns.

## 6. Acceptance drill and release evidence

Use isolated Compose projects, synthetic evidence, a reproducible placement seed and independent vendor ledgers that survive restart. Capture peak active requests, starts by time, operation IDs, cache hits, evidence revision, result and billable units. Database rows and Restate journals alone cannot prove what reached the vendor.

| Drill | Evidence required to pass |
| --- | --- |
| Normal weighted and primary/backup routing | Unit-test all bucket boundaries and a large fixed cohort against predeclared tolerance. Run a small, preselected 80/20 cohort end-to-end with independently computed expected assignments and enough headroom to avoid throttling. Replays preserve choices. A single-eligible case always selects its eligible route. Run the ordered policy separately and verify A-first routing, diversion to B, and return to A for new cases after recovery. |
| A down, B capped | Force A unavailable before send. Eligible new work diverts; lack of an authorized B reference produces zero B calls. Saturate B across two workers and show its parent/child caps, rolling budget and spend ceiling from independent records. Excess work either completes in budget or reaches an explained block. Advance past deadline and show no stray send. |
| A accepted, reply lost | Interrupt the worker at two barriers, once after SQL admission but before HTTP and once after A saves the operation but before Restate journals the reply. Before further retries, verify zero submissions in A's ledger at the first barrier and exactly one accepted A operation at the second. In both cases inspect the outstanding staff entry, replay on A's ID and lookup progress during submission backlog. Exercise both policies for a B replacement. In the permitted case, B has its own ID and reference and both operations remain linked. Verify duplicate deliveries, conflicting results and one billing reservation per contract unit. Race A and B for the last permitted attempt and prove that only one send is authorized. |
| A degrades, then recovers | Drive high latency as well as technical errors. Use fixture-only ramp targets such as 5%, 20%, 50%, 80%, with explicit per-stage minimum samples, dwell and p95/error thresholds. Hold at a stage with insufficient evidence. Force a bad probe or a regression mid-ramp, observe rollback, then recover. Queued or accepted B operations finish at B. Releasing backlog respects B and A caps. [Circuit-breaker recovery](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker) |
| Shared accounts and spend | Make two distinct routes share an upstream account and leave their breakers independent. A shared 429 delays both; a route-specific outage isolates A. Verify start counts across rolling window boundaries, concurrent last-unit reservations, lookup headroom, uncertain charges and billing-period rollover. |
| Sanctions lost response and late hit | First run the legacy scenario. Next, opt a fresh case into the strict policy, lose the original A response and allow a linked B screen to clear. Race B's completion with A's hold. Assert zero `APPROVED` revisions or approval webhooks while A is unresolved, assignment at the age threshold, and exactly one investigation for A's eventual hit. A definitive fenced non-acceptance or definitive clear can release the hold through the normal rules; an inconclusive result requires a recorded authorized disposition. [Original drill](../../../scripts/reconciliation_smoke.py) · [Restart drill](../../../scripts/sanctions_restart_smoke.py) |

Create the strict sanctions obligation durably before A's first possible send and before any B replacement becomes dispatchable. Use the same case row lock or equivalent version fence when arming or resolving the hold, applying any fresh or reused result, and publishing any approval/outbox event. Race these transactions in both orders. A late hit keeps this case in investigation pending disposition and creates one work item. A separate read of outstanding operations before an approval transaction would leave a race. A timeout, queue acknowledgement or traffic override cannot clear it. An inconclusive *authoritative terminal* response can enter the pinned review process. A nonterminal unknown remains on hold through escalation.

## 7. Rollout, rollback and publication

1. Add schema and backward-compatible readers first. Replay stored v1/v2 data, pipelines and single-binding issuer payloads. Keep the old deployment and original vendor routes available for active invocations and result lookups. Historical policies, decisions, receipts and event IDs must remain readable.
2. Introduce a versioned worker with routing disabled by default. Compare prospective choices in shadow mode without provider calls, spend reservations or case transitions. Enable two synthetic address vendors for one institution and product, then expand only verified contract groups. Keep the case and provider attempt in distinct Restate namespaces. Compare old and new outputs for unambiguous single-vendor cases.
3. Make the transition **per real upstream account**. Legacy workers and uncapped legacy lookups can otherwise consume the same contract outside the new rules. Use separate pilot credentials or drain/fence legacy dispatch for that account before cutover. Verify rule changes at runtime, including a lowered cap admitting new work only as existing work completes.
4. Roll back by stopping new placements for the affected policy/account and routing fresh cases through a known-good version. Keep the compatible worker, rate/spend state, evidence bindings and lookup routes alive for work already sent. Rehearse rollback with A and B both outstanding; neither an irreversible send nor an approved case is erased by rollback.
5. Regenerate Liam from the migrated database and update the schema assertion for new tables and relationships. In the talk, show the Rust call that applies the Restate concurrency scope and both SQL excerpts for the contractual rolling rate and the fenced recovery probe. Link both excerpts to the implementation and make the Scenario lab action open the real routing drill. Preserve the short/full routes, source line synchronization and clearly labeled recorded fallback.
